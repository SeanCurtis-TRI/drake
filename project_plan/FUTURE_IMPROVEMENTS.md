# FUTURE_IMPROVEMENTS — Making bCENIC competitive for real-time codimensional simulation

_Full critique of the barrier-CENIC (bCENIC) method as implemented on this branch, and a
prioritized path to real-time performance. Sources: the E1–E7/P1/P2 campaign data under
`project_plan/data/`, the reports (`ANALYSIS.md`, `PAPER_NOTES.md`, `HERO_DEMO.md`,
`THINGI10K_CLUTTER.md`, `docs/CCD_ROBUSTNESS_PLAN.md`), and a static audit of the hot-path code.
No new simulations were run. Numbers derived here (rather than quoted from a report) are marked
**[derived]**._

**Target:** real-time (RTR ≥ 1, ideally with margin) with several codimensional objects, robust
enough for teleoperated robot interaction — i.e. the E7 dishrack regime and P1-style layered
thin-object contact, sustained through the contact-rich phases, on one machine that is also
running the rest of the robot stack.

---

## 1. Verdict up front

The method's *architecture* — convex barrier contact + step-rejection CCD giving non-penetration
by construction — is sound and worth keeping. Its current *implementation and discretization* are
1–3 orders of magnitude away from the target, for reasons that are now well understood and mostly
addressable:

| Regime | Measured | Gap to RT |
|---|---|---|
| Hero dishrack (dual Panda, rack + utensils), default barrier 1e-4, acc 1e-1 | mean RTR 0.89–1.05; **windowed RTR 0.48–0.58 during the manipulation phase, bottoming at 0.19–0.34** [derived from `times.csv`] | 2–5× during the part that matters |
| Same scene, barrier 1e-3 | mean RTR 2.7–3.4, but bottoms at 0.44 in the busy window [derived] | ~2× at the minimum, and a thicker layer changes contact behavior |
| P1 washer stack (2–6 washers, layered near-coplanar) | 156–738 **ms per step** [derived from `data/P1_washer_stack/`] | 30–160× the per-step cost of sphere-on-plane (E1: 4.6 ms/step) |
| E4 nut & bolt (two bodies!) | 5.5 s/step, 67–1280 s wall per sim-second, up to **55,437 simultaneous constraint pairs** [derived] | 10²–10³× |
| E3d clutter | wall ∝ N^2.8 [derived]; 100 objects = 551–635 s/sim-s | 10²–10³× |
| P2 sheet in slot (single thin contact) | RTR 6–45 | already fast — small constraint sets are fine |

The contrast between the last two rows is the whole story: **the method is real-time capable when
the constraint set is small, and collapses when thin-layer contact generates large ones.** The
dominant problem is exactly the one suspected: the number of constraints generated by
hydroelastic-style intersection of the thin boundary layers (§3.1). But it is not the only
problem — the step-rejection economics (§3.3), the solver's per-iteration structure (§3.4), a
handful of high-impact code defects (§4), and contaminated measurements (§5) each contribute
multiplicatively.

## 2. Where the time goes — the measured picture

The one runtime-share number in the reports — “convex solve 57%, model update 27%, CCD 15%”
(`ANALYSIS.md:441`) — is a mean of per-run ratios over a subset of experiments (it excludes E7 and
E3e) and is **not representative of any regime the target cares about** [derived]:

| Scene | convex solve | model update (geometry + assembly) | CCD feasibility |
|---|---|---|---|
| E7 hero dishrack (barrier runs) | ~33% | ~25% | **~39–42%** [read from `plots/E7_hero_dishrack/runtime_breakdown.png`] |
| E4 nut & bolt | ~3% | **~95%** | ~1.6% |
| E3d 100-object clutter | **~88%** | ~3% | ~8% |
| E3e wild meshes, acc 1e-3 | 13–16% | **82–85%** | 1.4–1.9% [from surviving `stdout.log` timers] |
| E2 sphere-and-spiral | ~9% | ~28% | **~63%** |

Every phase is the bottleneck somewhere in the target envelope. Three cross-cutting facts:

- **One Hessian factorization per Newton iteration, everywhere.** `hessian_factorizations ==
  solver_iterations` exactly, in every run that records both (e.g. `data/P1_washer_stack/*.tsv`:
  245/245, 414/414, 631/631) — `enable_hessian_reuse{false}` (`icf_solver_parameters.h:60`).
- **Line search is most of the pair work.** Measured total-linesearch-iterations per solve: 1.15×
  Newton iterations (E1) → 2.25× (E7) → 3.7× (E3d-40) → 4.9× (E3d-100) [derived from `steps.tsv`].
  Each line-search iteration re-evaluates the *full* per-pair pipeline (§4, P0-2). At the
  100-object scale, ~83% of per-iteration pair work is line search.
- **Newton iterations grow with contact complexity**: ~3/solve (single sphere) → 7.3 (hero) →
  14.4 (40 objects) → 19.7 (100 objects), max 67 in a single solve [derived]. Conditioning grows
  the same way (max cond 9.8e4 → 3.6e7 (hero) → 3.3e10 (clutter) → 5.4e16 (E3e β=0.001)).

And one caveat that taints all of it: the campaign driver ran with `collect_heavy_stats = True`,
which computes a **dense O(nv³) `MakeDenseMatrix().ldlt().rcond()` on every Newton iteration,
inside the `cenic_time_solve` timing window** (`icf_solver.cc:360-363`; §5). The 57%-solve share,
and every published wall time, includes instrumentation cost.

## 3. Formulation-level critique

### 3.1 Constraint generation: one pair per intersection-surface vertex (the headline problem)

The discretization creates **one ICF constraint pair per contact-surface vertex**
(`icf_builder.cc:366-369`: `num_pairs_per_patch.push_back(s.num_vertices())`), where the contact
surface is the equilibrium surface of the intersection of two extruded thin volumes.

For two thin layers face-to-face — the defining configuration of this method — that surface is the
**arrangement of both meshes' triangulations restricted to the overlap region**: vertices of A +
vertices of B + all edge–edge crossings. Its vertex count is Θ(everything in the overlap), with a
constant of roughly 2–6× one plate's vertex count in that region [derived, §1 of the code audit].
Consequences, all confirmed in data:

- **Constraint counts are set by mesh resolution, not by contact physics.** A two-body threaded
  interface (nut & bolt) carries 55k pairs; ten stacked codim cups (E2 cones) carry 20k; the
  Thingi10K clutter runs 7k–24k (“an order of magnitude beyond primitive clutter” —
  `THINGI10K_CLUTTER.md:136-140`), at ~1–2 pairs per mesh face in contact [derived].
- **Refining either mesh 2× per axis quadruples the constraint count**, which quadruples
  per-Newton-iteration cost *and* worsens conditioning, which raises the iteration count. There is
  no cap, no clustering, no adaptivity — cost/step scales as contacts^~2.5 along the matched
  clutter ladder [derived], which compounds into the observed wall ∝ N^2.8.
- **The thin-layer representation costs 2.7–6.4× the volumetric fallback inside the same solver**
  (E3b barrier sweep, `ANALYSIS.md:79-93`) with a 3–5× constraint-count multiplier — the fairest
  in-repo ablation, and it is unfavorable. On the hero scene the default barrier runs RTR 1.05 vs
  volumetric 2.18 at its artifact-free accuracy.

Physically, most of these constraints are redundant. In a resting face-to-face patch the pressure
field is nearly constant over the interior; the information content of the patch is a net wrench
plus a contact-boundary shape. Spending one log/sqrt/10-division kernel evaluation per mesh vertex
per line-search iteration to represent that is the single largest waste in the method. §6 Phase C
is the fix.

A second-order aspect of the same issue: the **barycentric dual quadrature requires a stitched
surface**, which is what forced the fork to add vertex deduplication into the surface builder —
implemented as a Θ(V²) linear scan with a sqrt per comparison (§4, P0-1). So the discretization
choice does not just create too many constraints; it also made the geometry stage quadratically
expensive to build them. Note the planned quadrature ablation (naive vs barycentric-dual,
`PAPER_NOTES.md:148-152`, planning doc §"method figures") was never run — the paper currently has
no evidence that the expensive quadrature buys accuracy.

### 3.2 The geometry pipeline rebuilds the world twice per step

Per accepted error-controlled step there are **two full `UpdateModel` calls** (t₀ model + half-step
model, `cenic_integrator.cc:403-418, 518`), each of which:

- recomputes every contact surface from scratch via the **volume**-BVH path
  (`field_intersection.cc:217-252` — the cheaper surface-BVH+BFS overload at `:254-372` exists and
  is unused). For extruded slabs the volume BVH degenerates: every tet of A in the overlap
  footprint collides with the 9–18 B-tets stacked in the same footprint, with no depth pruning —
  the slab geometry defeats the hierarchy;
- pays ~6 heap allocations and ~3 sqrt per candidate tet pair (`field_intersection.cc:86-198`),
  then the Θ(V²) dedup, then allocates a fresh mesh + field + two gradient arrays per surface
  (`field_intersection.cc:432-500`);
- re-derives geometry-invariant material properties through string-keyed property maps per surface
  (`icf_builder.cc:685-699`), bypassing the version-keyed cache that the point-contact path
  already has (`icf_builder.cc:1084-1110`).

There is no temporal coherence anywhere: no caching of the contact-surface topology, no
incremental update, no reuse between the two per-step rebuilds, no memory pooling. In the regimes
where this stage dominates (nut & bolt ~95%, E3e tight-accuracy 82–85%), the method is not
solver-bound at all — it is an allocation- and arrangement-computation benchmark.

### 3.3 Step economics: pay-then-discover, three solves per step, and the accuracy paradox

The integrator's control flow charges full price before learning a step was doomed:

- **CCD rejections are discovered after a complete solve.** A full-step CCD rejection wastes
  ~25% of a step's work; a half-2 rejection wastes ~95% [derived from the DoStep structure,
  `cenic_integrator.cc:313-566`]. On the hero default run there are 4,435 CCD rejections against
  2,754 accepted steps — **~62% of full-step solves are thrown away** [derived]; at barrier 1e-5
  it is 23,555 rejections for 10,608 steps. Nothing predicts infeasibility before solving, even
  though a conservative pre-solve bound (current velocities × h vs. remaining clearance) would
  catch most of these for pennies.
- **Error control costs 3 solves per accepted step** (full + two halves, Richardson) plus a second
  `UpdateModel`. At tight accuracy the *outer* loop also discards work: 2,798 EC rejections on
  6,541 accepted steps ≈ 30% of attempts (E7 acc 1e-3).
- **The two rejection mechanisms fight each other** — the documented accuracy paradox
  (`THINGI10K_CLUTTER.md:120-129`): at loose accuracy the error controller proposes big steps that
  CCD throws away (74–108 CCD vs ~0 EC rejections); at tight accuracy the balance inverts. Net:
  acc 1e-1 is often *slower* than 1e-2. The step-size policy is fundamentally uninformed about the
  barrier layer: the controller optimizes LTE while the binding constraint is "do not cross a
  200 µm shell."
- **`use_toi` defaults off**, so every CCD rejection blindly bisects instead of stepping to
  0.95·TOI — despite E6b/E3e evidence that TOI-on reduces rejections and wall time.
- **Fixed-step mode has no CCD gates at all** (they live in the error-control branch). For teleop
  the natural operating point is fixed-dt; today that operating point silently forfeits the
  non-penetration guarantee that is the method's reason to exist. This is an architecture gap, not
  a tuning gap.
- The solver is asked for 1000× more precision than the integrator needs: solve tolerance =
  `κ·accuracy` with hard-coded κ = 1e-3 (`cenic_integrator.cc:584-588`).

### 3.4 The solve: exact Newton with exact line search, no reuse, no parallelism

- **Exact line search on every iteration**, `max_linesearch_iterations = 100`,
  `linesearch_tolerance = 1e-8` — and each line-search iteration evaluates the *full* per-pair
  data pipeline including the 3×3 per-pair Hessian and its 6×6 shift, only to contract everything
  against a single vector for two scalars (§4, P0-2). Convexity is the method's selling point
  precisely because it makes cautious globalization unnecessary — an Armijo backtrack or a
  fused cheap directional evaluation would preserve the guarantee at a fraction of the cost.
- **One factorization per iteration** (reuse machinery exists and is off). The factorization
  itself is a block-sparse right-looking Cholesky over `MatrixXd` blocks with per-block heap
  allocation and per-update expression temporaries (§4, P1-3) — not supernodal, no fixed-size
  `Matrix6d` specialization even though every free-body clique is 6×6.
- **The per-pair kernel runs at ~0.4–0.6 flops/cycle** [derived: ~216 ns/pair-eval on E7,
  ~145 ns on clutter, vs ~280 flops]: one log + one sqrt + ~10 divisions per pair per evaluation,
  loop-invariant quantities recomputed every evaluation, per-pair state scattered across ~19
  parallel `std::vector`s (≈19 cache lines per pair), data-dependent branches, hot-path NaN
  checks with `throw` (which also blocks vectorization), and zero SIMD.
- **Zero threading anywhere in ICF/CENIC or contact-surface computation** (grep-confirmed; the
  contact-surface loop even carries an upstream `TODO: try some thread parallelism here`,
  `proximity_engine.cc:1153`). All published numbers are single-core numbers from a 64-core
  machine; the campaign got its parallelism by running 16 *simulations* concurrently — which also
  contaminated the comparisons (§5).
- Conditioning: the 1/β² law is confirmed (E1), and the reports treat cond ≈ 5×10¹⁶ as survivable
  (`THINGI10K_CLUTTER.md:110-113`). In double precision that is zero guaranteed digits; "the
  Cholesky did not throw" is not the same as "the search direction was meaningful." The near-rigid
  continuation absorbs *physical* stiffness well (E3c: flat conditioning across E = 1e5→1e11), but
  contact-count growth and thin plates still drive conditioning up 3+ decades, and iteration
  counts follow.

### 3.5 Parameter coupling: one thickness, three jobs

`margin + barrier` simultaneously sets (a) the passable clearance, (b) the CCD rejection rate, and
(c) the contact stiffness profile:

- **Capability limit (measured, P2):** a thin sheet cannot traverse a slot with per-side clearance
  below 2×(margin+barrier) = 0.4 mm at defaults — it stalls mid-slot at 1.5× and jams at the
  entrance at ≤1×, with *zero* CCD rejections (the failure is force-based: the sheet must climb
  two opposing barrier potentials). For teleop insertion tasks (thin objects into racks, exactly
  the hero use case) this is a hard functional limit, not a performance one.
- **RTR limit (measured, E7):** thinning the barrier 1e-3 → 1e-5 collapses RTR 3× → 0.31× almost
  entirely through CCD rejections. So one cannot buy back the clearance limit by thinning the
  layer without destroying the step rate.
- **Robustness limit (measured, E3e/E7):** impacts pierce thin layers — e₀ reached 2.0 (the
  log-barrier singularity / rigid-core value) in 12/16 Thingi10K cells, which were then re-tuned
  (10× thicker barrier, TOI on, smaller stacks, shorter drops) to pass; **the hero demo itself
  hits e₀ = 2.0000 in four runs** [derived from `steps.tsv` `max_e0`], i.e. the flagship scene
  operates at the singularity and no report mentions it. The startup rule "barrier must not be
  small relative to initial penetration" (`HERO_DEMO.md:117-123`) is a symptom of the same
  coupling.

A competitive method needs these decoupled: geometric admissibility set by geometry (not by a
force-layer thickness), safety set by CCD, stiffness set by material parameters.

### 3.6 What is genuinely good (keep it)

- The **guarantee architecture**: convex solve + reject-and-shrink CCD gives zero penetration by
  construction, with the CCD layer now hardened, independently verified (2.4M constructed-truth
  queries, 2M fcl-differential comparisons, zero confirmed misses) and cheap at the kernel level
  (~190–200 ns/query, allocation-free).
- **Loose-accuracy robustness**: barrier hydro at acc 1e-1 is artifact-free where volumetric needs
  1e-3 (E7 observation 4 — the volumetric acc-1e-1 run shows 4× inflated contact counts from
  sink-in).
- **β-capped stiffness**: conditioning flat across six decades of modulus (E3c) — a real
  robustness result.
- Several pieces of the pipeline are already well-optimized (Hessian assembly avoids temporaries;
  `EigenPool` is contiguous; error estimate is allocation-free) — the problems are concentrated,
  not diffuse.

## 5. Measurement integrity — fix before quoting anything

The critique above is only as good as the data, and the data has known defects:

1. **Instrumentation inside timers** (P1-1): every campaign run paid a dense O(nv³) rcond per
   Newton iteration, attributed to `cenic_time_solve`. The published shares and wall times are
   upper bounds of unknown looseness.
2. **Concurrent-run contention** [derived from `meta.json` timestamps]: the E7 comparison mixes
   runs executed solo with runs executed alongside 7–11 other simulations on the same host. The
   headline "barrier=1e-3 beats volumetric acc=1e-3" compares an 11-way-contended run against a
   7-way-contended one; "default barrier 1.05 vs volumetric 2.18" compares solo vs 7-way. No
   report acknowledges this.
3. **All campaign data predates the X5/X6 fixes** (4× full pose-map copies per step are in every
   published CCD number) and predates the ICF point-pair dispatch fix; raw per-phase timer logs
   were deleted for everything except E3e.
4. **Windowed vs mean RTR**: mean RTR flatters the barrier runs; the windowed curves show every
   barrier configuration below real time in the manipulation-heavy phase. RT claims must be made
   on windowed minima/percentiles, not run means.
5. **Missing entirely**: any third-party baseline (MuJoCo / IPC / ABD — `PAPER_NOTES.md:6` "No
   third-party software was run"), the in-repo discrete-SAP comparison (P6), the quadrature
   ablation, any memory/RSS/fill-in data, any multi-core data, the P5 energy audit of the barrier
   layer, and the P1 conditioning-vs-N column that was the point of the washer experiment.

**Action:** re-run a small benchmark matrix (hero @ 3 configs, P1 @ N=2/4/6, E3d @ 20/40, E4 @ 1
config) single-run, heavy-stats off, post-X6, with raw timers retained, plus
`--integrator=discrete` rows — this becomes the baseline all Phase B–F gains are measured against.
~Half a day of compute; without it every optimization claim is unanchored.

## 6. Roadmap

Ordered so each phase de-risks the next; expected gains are multiplicative where independent.
"RTR×" estimates are against the corrected baseline of Phase A.

### Phase A — Measurement + free knobs (days)

1. Fix P1-1 (heavy-stats out of timers, `Clear()` bug, per-step max-cond computed per step);
   re-derive the phase shares per regime (§5 action).
2. Flip the three already-implemented switches and measure: `enable_hessian_reuse = true`,
   `use_toi = true` (E6b/E3e evidence both favor it), κ (solver tolerance / accuracy ratio)
   1e-3 → 1e-2.
3. Delete/gate X1/X3 hot-path diagnostics (P2-3).

_Expected: 1.3–2× overall, plus trustworthy numbers._ Risk: near zero.

### Phase B — Hot-path engineering, no behavior change (1–2 weeks)

1. P0-1 spatial-hash vertex dedup (Θ(V²)→Θ(V)) — transforms the scaling curve, not just the
   constant.
2. P0-2 fused line-search kernel; replace exact line search policy (α_max accept fast path exists;
   add Armijo backtrack fallback with ≤3 evaluations instead of Newton-with-bisection to 1e-8).
3. P0-3 per-pair invariant caching + shared reciprocals; pack the hot per-pair scalars (P2-4).
4. P1-3 factorization: `Matrix6d` block specialization, `AddToBlockNoAlias`, scratch buffers in
   factor/solve.
5. P1-4 allocation pooling in `field_intersection` + surface mesh/field reuse across the two
   per-step rebuilds.
6. P2-1/P2-2 CCD: generation-counter invalidation, flat BVH node storage, skip anchored/unmoved
   participants, hoist per-participant vertex transforms.

_Expected: model update 5–50× at scale (dedup dominates), solve 2–4×, CCD 2–4×. Combined ~3–6× on
hero-class scenes; more where the dedup was binding (clutter, nut & bolt). Brings hero
manipulation-window RTR from ~0.5 to ~1.5–3, washers from 0.02–0.06 to ~0.1–0.3._ Risk: low —
all mechanical, all behavior-preserving, all verifiable against existing test suites.

### Phase C — Constraint budget: break the resolution↔cost coupling (2–4 weeks) ⟵ **the decisive phase**

The formulation fix for §3.1. Insert a quadrature-reduction pass between contact-surface
computation and `SetPairLogBarrier`:

1. **Moment-matched patch decimation.** For each contact patch, cluster the per-vertex quadrature
   set down to a budget of K points (K ≈ 16–64, parameter), preserving per-cluster ∑Ae (zeroth
   moment), ∑Ae·p (first moment / center of pressure), area-weighted normal, and area-weighted
   e₀/δ. Keep a denser ring at the patch boundary (where the extent field's gradient — and all the
   contact-transition information — lives) and coarse interior points. The per-point cost model is
   unchanged, so **convexity and the barrier guarantee are untouched**; only the quadrature of the
   patch integral coarsens. Greedy area-weighted clustering on the (already stitched) surface is
   O(V log V) — cheaper than what the dedup used to cost.
2. **Cap-and-refine policy:** patches under budget pass through unchanged (single-edge contacts —
   the P2/fast regime — see zero change); only large patches pay the clustering. Expose
   `max_pairs_per_patch` in `IcfSolverParameters` so the paper can show the accuracy/cost Pareto
   (this is also, finally, the quadrature ablation the paper plan asked for).
3. **Validation:** P1 washer stack (stack stability + settle height vs K), P2 traversal threshold
   (must not shift), E4 nut & bolt (kinematics of threading vs K), momentum/energy sanity on E1.
   The barrier force field changes at coarse K; the claim to defend is that K ≈ 32 reproduces
   K = ∞ behavior to within error-control tolerance — the patch interior really is
   low-information.

_Expected: nut & bolt 55k → ~10² pairs (≥100× on its two dominant stages); washers ~10–30×; hero
~1.5–3× (its patches are moderate); clutter cost/step becomes ~linear in contact area rather than
mesh resolution._ This is the phase that makes layered thin-object scenes real-time-plausible.
Risk: moderate — behavior changes with K; mitigated by the pass-through for small patches and the
Pareto study. Fallback if clustering proves fiddly: a fixed-resolution resampling grid per patch
(simpler, slightly less accurate boundary handling).

Complementary (cheaper, additive): **length-scale-aware surface computation** — route
compliant-compliant intersection through the surface-BVH+BFS overload that already exists
(`field_intersection.cc:254-372`), which walks the contact manifold instead of colliding two
degenerate slab BVHs.

### Phase D — Step economics for a teleop profile (1–2 weeks)

1. **Fixed-step mode with the CCD guarantee**: move the feasibility gates out of the
   error-control-only branch; on rejection, substep (h/2, h/4, … or 0.95·TOI) *within* the fixed
   frame budget rather than failing the frame. This is the operating mode teleop actually needs —
   fixed 2–5 ms physics dt, bounded worst-case work per frame, guarantee intact.
2. **Predict-then-clamp CCD**: before the solve, bound each body's swept motion (‖v‖h + ‖ω‖h·r
   against remaining clearance from the broadphase); clamp h proactively instead of solving and
   rejecting. Kills most of the 62%-wasted-solves economics of §3.3. Conservative, cheap
   (participants only, reuses CCD broadphase data).
3. **Skip-CCD fast path**: when the conservative swept-motion bound of every participant pair is
   below a fraction of the layer thickness, skip the narrowphase entirely (sound; most teleop
   frames are quasi-static). Directly attacks the ~40% hero CCD share.
4. **Cheaper error control** for the error-controlled profile: reuse the half-1 solve as the
   embedded estimate against the full step (2 solves/step instead of 3; one order lower estimate,
   acceptable at teleop accuracies), or Richardson every k-th step.

_Expected: 1.5–2.5× on hero-class scenes; bounded per-frame latency (the actual teleop
requirement, which RTR means alone don't capture)._ Risk: low-moderate; the CCD-gate relocation
needs care to preserve the guarantee proof structure.

### Phase E — Parallelism (2–3 weeks, after B/C so the serial profile is honest)

1. Thread the per-patch loops (`CalcData` / fused line-search kernel / `AccumulateGradient`
   reduction) — disjoint writes, trivial partition.
2. Thread `MaybeMakeContactSurface` over candidate pairs (upstream TODO; result slots pre-sized).
3. Thread CCD narrowphase over geometry pairs.
4. Contact-island decomposition: independent islands → independent Hessians → parallel small
   factorizations (teleop scenes are many small islands, not one big one); also caps conditioning
   per island.

_Expected: 4–8× on desktop cores for the parallel stages; with B+C+D this is what buys headroom
(RTR ≫ 1) rather than bare feasibility._ Risk: moderate (determinism policy needed — fixed
partition + ordered reduction keeps runs reproducible).

### Phase F — Formulation research (4–8 weeks, contingent on C/D results)

Only if C+D+E leave a gap, or to remove the §3.5 coupling at its root:

1. **Nodal field-sampling contact** (codim-IPC-style): replace the volume–volume intersection
   surface entirely — sample body B's extent field at body A's collision-mesh vertices (and
   symmetrically); each in-band sample becomes one barrier pair with the field value as e₀ and
   the field gradient as the normal. Kills the arrangement computation, the dedup, and the
   resolution coupling in one move; constraint count = vertices inside the band, directly
   controlled by a contact-proxy mesh resolution. Cost: a new quadrature consistency story
   (area weighting from vertex duals of a *single* mesh — already implemented for the dual
   quadrature) and re-validation of the contact-force field. This converges the method toward the
   IPC family while keeping the convex ICF solve and the CCD guarantee — arguably the natural
   end-state of the formulation.
2. **Decouple clearance from stiffness** (§3.5): allow the *force* layer (barrier) to be thinner
   than the *safety* layer (CCD margin), letting sheets pass tight slots while CCD still protects
   crossings; requires the predict-then-clamp machinery from D2 to keep rejection rates sane, and
   an impact-robust answer to the e₀→2 pierce mode (e.g. TOI-projected impact substep instead of
   barrier-absorbs-everything).
3. **GPU batch evaluation** of the per-pair kernel + batched island solves — only worth designing
   after C fixes the constraint counts (10⁴–10⁵ cheap pairs is a GPU-shaped problem; 10²–10³
   moment-matched pairs is not).

## 7. Summary for the impatient

1. **Trust nothing until Phase A**: the published timings include per-iteration dense-rcond
   instrumentation, 16-way host contention, and pre-X6 pose copies; the per-step condition-number
   plot data is a running max (bug).
2. **The formulation's real liability is that constraint count = contact-surface vertex count =
   mesh-arrangement complexity** — 55k pairs on a two-body scene is not a solver problem, it is a
   discretization problem. Moment-matched patch quadrature reduction (Phase C) fixes it without
   touching convexity or the guarantee.
3. **Three specific code defects are quietly super-linear or dominant**: the Θ(V²) vertex dedup,
   full-Hessian work inside every line-search evaluation, and the O(all-nodes) CCD cache reset.
   Fixing those three plus the free knobs is worth ~3–6× before any formulation change.
4. **The step-rejection economics are backwards for the barrier regime**: predict-then-clamp
   instead of solve-then-reject, TOI on, and a fixed-step teleop mode *with* the CCD gates.
5. With B+C+D+E compounded, hero-class teleop scenes land at sustained RTR ≥ 3 and layered
   thin-object scenes at ≥ 1 on a desktop CPU — competitive for the stated use; the nodal-sampling
   reformulation (F1) is the long-term convergence point with codim-IPC, and GPU only makes sense
   after the constraint counts are fixed.
